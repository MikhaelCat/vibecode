# Архитектура

Документ описывает, как устроен проект и где искать код. Он намеренно короткий:
одна страница на каждый слой, без истории разработки и ролей команды.

## 1. Общая картина

```
браузер
  │  POST /api/plan (SSE) / POST /api/plan/sync (JSON)
  ▼
src/api ──────────────► src/agent (orchestrator)
                          │  guard → intent → tool calls
                          ▼
                     src/tools/providers ──► интернет (OSM/Overpass, Wikipedia,
                          │                   Nominatim/Photon, Яндекс.Погода/Open-Meteo, OSRM,
                          │                   VL.ru, Яндекс Карты — с ключом)
                          │  ToolOutput (live/cache/mock/stale/estimated + summary)
                          ▼
                     src/domain::Facts
                          │  submit_plan
                          ▼
                     src/domain::plan::enrich → validate (V01–V18) → repair/fallback
                          │
                          ▼
                     SSE plan ──► src/frontend (SPA + Leaflet)
```

Ключевое правило: **ни один HTTP-обработчик и ни один кусок фронтенда не
ходит во внешний API за данными напрямую**. Все данные проходят через
инструмент, получают `place_id` и источник, попадают в `Facts` и только
потом — в план. Благодаря этому валидатор может проверить каждую точку.
Из сети фронтенд берёт только саму библиотеку Leaflet и тайлы карты.

## 2. Backend

Папки: `src/api/`, `src/agent/`, `src/domain/`, `src/store/`, `src/llm/`,
конфигурация — `src/config.rs`.

### API (`src/api`)

- `POST /api/plan` — SSE: `stage`, `intent`, `tool_call`, `tool_result`,
  `plan`, `validation`, `usage`, `refusal`, `done` (события `error` нет).
- `POST /api/plan/sync` — то же без стрима, для эвалов и отладки.
- `GET /api/health`, `/api/stats`, `/api/runs/{id}` — диагностика;
  `health` открыт всегда, `stats` и `runs` требуют токен, если задан `APP_TOKEN`.
- Статика: `WEB_DIR` отдаётся `ServeDir` с SPA-fallback на `index.html`
  (если `index.html` нет, при старте пишется ошибка в лог, а `/` отдаёт 404).
- Размер тела ограничен 16 КиБ; POST защищён `APP_TOKEN` (если задан);
  на прогон стоит общий семафор `CONCURRENT_RUNS`; SSE-прогон жёстко
  ограничен 300 с, `/api/plan/sync` — теми же 300 с. Обрыв SSE-клиента
  отменяет прогон: он дропается, в БД не пишется и освобождает слот.

### Агент (`src/agent`)

`orchestrator` — единственный путь к плану:

1. проверить запрос (`guard` → `domain::intent::parse`, без LLM);
2. применить переопределения из формы (`RunOverrides`: даты и транспорт
   авторитетны и ограничивают поездку 7 днями);
3. собрать контекст: системный промпт, `INTENT_JSON`, `PLAN_WINDOW`
   (авторитетный период) и текст запроса;
4. заранее подтянуть афишу (`find_events`) для городов из запроса (таймаут 6 с);
5. в цикле до `MAX_STEPS`: вызвать LLM, выполнить независимые tool calls
   параллельно (`join_all`), каждый успешный результат отправить в `Facts`;
6. `submit_plan` разворачивается через `plan::enrich` и проверяется `validate`;
7. hard-нарушения возвращаются модели как feedback — до `MAX_REPAIRS` ремонтов;
8. если план так и не принят — `fallback::assemble` собирает degraded-план.

Правила цикла: терминальный `submit_plan` не даёт модели «рассказать» план
текстом в обход проверок; лимит поисковых вызовов (`search_places` +
`get_nearby_attractions`) — 12 на прогон, дальше тул отвечает ошибкой с
`source:"budget"`; результаты инструментов для модели ужимаются (проекция
полей и обрезка JSON до 12 000 символов); после сборки плана
`ensure_plan_events` догружает афишу городов, которые реально попали в план.

### Домен (`src/domain`)

- `intent` — даты (1–7 дней, `MAX_TRIP_DAYS`), транспорт, интересы (в том
  числе как OSM-теги), must_see, guardrails (`off_topic`, `other_region`,
  `injection`, `empty`, `too_long`). Хаб пишется в `assumptions`, только
  когда названо не больше одного населённого пункта и сам регион не упомянут.
- `facts` — проверенные места, погода, события, жильё, маршруты; каждый факт
  несёт провенанс (`live`/`cache`/`mock`/`stale`/`estimated`);
  `ensure_minimal` гарантирует план из `data/mock/*.json`, если всё упало.
- `plan` — `enrich`: `PLAN_WINDOW` авторитетен; дедупликация по `id`,
  нормализованному имени в радиусе 500 м и 50 м; отбрасывание воды и точек
  вне радиуса места. Радиус: `scope_km` населённого пункта (city 25,
  town 15, village 9, hamlet 6 км; на маршруте — минимум 15) или 40 км от
  центра хаба. Жильё — в пределах `LODGING_MAX_KM` = 45 км от точек плана;
  владивостокское жильё допускается, только если хаб не назван, назван
  владивостокский хаб или точка плана в пределах 30 км от Владивостока.
- `validate` — V01–V18 (расшифровка — в `docs/API.md`); hard-нарушения
  блокируют план, soft только понижают score.
- `fallback` — детерминированный план из `Facts`, если модель не справилась;
  при плохой погоде уличные точки заменяются indoor-местами.
- `settlements` + `hubs` — курируемый газетир 211 населённых пунктов
  (`data/geo/primorye_settlements.json`, координаты и `kind` из OSM) и
  11 агломераций с триггерами и приоритетным списком жилья
  (`data/geo/primorye_hubs.json`).
- `spatial` — k-d дерево: радиусные фильтры и поиск ближайших для
  инструментов, газетира и правил жилья.
- `routing` — перегоны дня как задача о кратчайшем пути: полный граф точек
  (рёбра — дорожное расстояние), Дейкстра от стартовой точки, улучшение
  2-opt и порядок с приоритетом запрошенных мест; используется fallback- и
  офлайн-планировщиком, чтобы день не «зигзагировал» через весь край.
- `geo` — «суша/вода» по GeoJSON края и суши, `waterbody_title`,
  haversine и оценочное время в пути.
- `dates` — Asia/Vladivostok: «сегодня», ближайшие выходные, месячные фразы.
- `trace` — `RunTrace`/`TokenUsage` для `/api/runs/{id}` и эвалов.

### Хранилище (`src/store`)

SQLite — источник истины:

- `runs` — запрос, статус (`plan`/`degraded`/`refusal`), задержка, токены,
  стоимость, `plan_json`, `trace_json`;
- `daily_budget` — дневные счётчики (пишутся при каждом прогоне; проверка
  лимита сейчас читает суммы из `runs` за владивостокские сутки).

Redis здесь не используется. Он живёт в `src/tools/cache.rs` и кэширует
только результаты инструментов; пустой `REDIS_URL` — память.

### LLM (`src/llm`)

Один трейт, две реализации: OpenAI-совместимый клиент (Spirit Proxy /
OpenRouter; 3 попытки с backoff, таймаут `REQUEST_TIMEOUT_SECS`) и
детерминированный `MockLlm`. `MOCK_LLM=1` подменяет только модель: инструменты
по-прежнему сначала идут в живые провайдеры и падают в `data/mock` только при
недоступности. Ключи читаются из `.env`, не логируются и не сериализуются;
без ключа (и без `MOCK_LLM=1`) сервис поднимается на `MockLlm`.

(её версия попадает в `/api/health` и trace) и `repair_v1.md`;
`system_v2.md` и `system_v3.md` выбираются конфигами `configs/*.toml` для
эвала; `preflight_v1.md` в рантайме не загружается.

## 3. Инструменты и парсинг

Папка: `src/tools/`. `registry` задаёт трейт `Tool`, `ToolCtx` и `ToolError`
(а `ToolOutput` живёт в `domain::facts`) и спецификацию `submit_plan`;
`providers` содержит по модулю на источник; `cache.rs` — необязательный общий
кэш. Реестр отдаёт модели 9 инструментов:

| Инструмент | Данные и порядок источников |
|---|---|
| `geocode` | Nominatim → Photon → локальный справочник (только при совпадении имени) |
| `search_places` | Яндекс Карты (с ключом; для еды, ночной жизни и заведений) → затем параллельно: тайлы OSM map API (ближайшие объекты, точные координаты), категорийный поиск Nominatim (до 50 объектов одной категории по всему району), Википедия geosearch (достопримечательные категории), Overpass (весь район одним запросом; стартует вместе с остальными и ждётся только при тонком ответе) → слияние без дублей (id и название ближе 300 м) → локальный справочник, если живой ответ тонкий |
| `get_nearby_attractions` | Википедия geosearch → локальные места в радиусе |
| `get_weather` | Яндекс.Погода (десятидневная страница города: температуры, ветер, условия, восход/закат; вероятность осадков выводится из описания) → Open-Meteo (даёт вероятность осадков числом) → VL.ru (ближайший город) → честное «прогноз недоступен» |
| `get_route` | OSRM (только `car`; `overview=full`, GeoJSON-геометрия строкой, опциональные `legs` для >2 точек) → оценка по haversine с мок-геометрией (LineString) |
| `find_lodging` | тайлы OSM вокруг ориентира + категорийные фразы Nominatim («гостиница», «база отдыха», «гостевой дом») в окне 35 км, параллельно Overpass по всему окну (ждётся только при тонком ответе) → локальный каталог; ранжирование ближайшими 15/35 км; цены — демо-оценки по населённому пункту и типу жилья (`DemoPrices` в `lodging.rs`) |
| `find_transport` | локальный справочник `data/mock/transport.json` (демо) |
| `find_fuel` | тайлы OSM у точек маршрута (точные координаты станций) → Overpass по коридору (одним запросом, best-effort) → локальный справочник; координаты всех строк — реальные станции OSM (`osm_node`), наличие и цены — демо-оценки |
| `find_events` | VL.ru, JSON-LD schema.org Event по городам афиши |

Правила инструментов:

- координаты обязательны, конечны и лежат в Приморье; точки из OSM map API
  проходят строгий land-маск (без прибрежного допуска);
- `(0,0)` и неизвестные места не становятся точками плана;
- **озеро, река, бухта и море — это районы поиска, а не маркеры в воде**:
  провайдеры отбрасывают водные названия, а `enrich` повторно чистит точки
  из устаревших кэшей;
- каждый набор результатов фильтруется радиусом разрешённого района через
  k-d дерево (`domain::spatial`), ближайшие — первыми; на «ближайшее/поблизости»
  дерево отдаёт k ближайших вместо всей выдачи;
- радиус выдачи зависит от транспорта и длины поездки (`plan::trip_radius_km`:
  пешком 20 км, велосипед 50, автомобиль 60 км × дни (максимум 300), транспорт
  70 км × дни (максимум 400)) — так двухдневный план не растягивается на полкрая;
  это правило использует и детерминированный fallback, и офлайн-модель;
- бары и клубы попадают в выдачу только по явной категории `bar`/`club`;
- дубликаты убираются по `id` и по названию в радиусе 500 м (`enrich`
  дополнительно — 50 м);
- локальные заглушки читаются только из `data/mock/*.json`; каждый результат
  помечен `live`, `cache`, `mock`, `stale` или `estimated`.

`resolve_area` (`providers/geo.rs`) разрешает район строго по порядку:
упоминание региона → известные природные объекты (Ханка, Раздольная) →
курируемый газетир населённых пунктов → агломерационные хабы → известные
районы (Ливадия, Врангель, Русский, Пидан) → Nominatim (1 запрос/с, кэш
30 минут) → Photon. Успешное разрешение тоже кэшируется на 30 минут;
молчаливого фолбэка на Владивосток нет.

Запрос по всему региону («по Приморью», без названного места) не отдаёт
список точек, растянутый на 1000 км: `search_places` подменяет такой район
базовым городом (Владивосток) и пишет об этом в summary, а модель может
явно запросить другие города, если поездка действительно идёт по краю.

`find_lodging` без населённого пункта возвращает пустой список и просьбу
назвать место, а не владивостокский отель по умолчанию. Ранжирование: сначала
варианты в 15 км, при нехватке (меньше двух) — до 35 км, ближайшие первыми,
подпись вида `Находка (20 км от Южно-Морского)`.

`search_places` следует за разобранным запросом: `orchestrator::enforce_search_intent`
подставляет названный город, категории из интересов и флаг `nearest`, а
спецификация `submit_plan` в `registry.rs` ограничивает `kind` значениями
`ItemKind`.

Кэш (`tools/cache.rs`) необязательный: Redis, при его отсутствии — память.
Ключ включает даты только для погоды и событий; кэшируются только `live`-результаты,
TTL 10 минут; попадание помечается как `cache` и в `meta`, и в `data.*.source`.

## 4. Frontend

Папка: `src/frontend/`. Без npm-зависимостей и сборщика: `index.html`,
`styles.css`, `app.js`; сборка — `npm --prefix src/frontend run build`
(копирует файлы в gitignored `dist/`), axum отдаёт `dist` из `WEB_DIR`.

- форма: даты (кастомный календарь, 1–7 дней), транспорт иконками, примеры
  запросов, счётчик символов, необязательный токен (показывается по `auth_required`);
- SSE читается через `fetch` + `ReadableStream` (код `EventSource` не подходит,
  потому что нужен POST), поэтому работает `x-app-token`; если поток рвётся,
  сервер отменяет прогон;
- план: дни, точки, переезды (текстом), события дня, варианты жилья, погода,
  предупреждения, честная плашка «нет связи»;
- карта создаётся лениво через `IntersectionObserver`, тайлы OpenStreetMap,
  Leaflet 1.9.4 подключается цепочкой CDN (jsDelivr → unpkg → cdnjs);
- маркер строится только для валидной точки внутри Приморья; водные названия
  и `(0,0)` пропускаются, поэтому пин не может оказаться в море;
- на мобильных однопалый скролл страницы не блокируется (карта пануется
  кнопками).

## 5. QA

- `tests/validator_cases.rs` — интеграционные тесты валидатора;
- `src/bin/eval.rs` — эвал-раннер и метрики; `configs/v1_baseline.toml`,
  `configs/v2_compact.toml`, `configs/v3_fast.toml` задают промпт, модель,
  шаги и ремонты; без `--live` используется `MockLlm`;
- `data/eval/` — `queries.jsonl` (20 запросов) и `guardrails.jsonl`
  (10 кейсов для ручной проверки отказов);
- `scripts/qa.sh` — fmt, clippy, тесты, сборка фронта, mock-сервер, smoke,
  браузерный тест и инварианты плана;
- `scripts/smoke.sh`, `scripts/edge_cases.sh`, `scripts/frontend_test.sh`,
  `scripts/eval_all.sh`, `scripts/docker_smoke.sh` — API-прогон, живые
  необычные запросы, вёрстка, эвалы, docker;
- `just check` / `just qa` — те же проверки через justfile.

Эвал по умолчанию работает на `MockLlm` и не тратит токены. Живой прогон
включается только явно (`--live`) и требует ключ в окружении.

## 6. Правила изменений

1. Новые данные — только через `Tool` и `Facts`, не напрямую из API/агента.
2. Новые категории — в схеме инструмента, промптах и `ItemKind`.
3. Любая точка плана должна иметь провенанс и координаты в Приморье (на суше).
4. Водоёмы не рисуются маркером в воде; радиус места (`scope_km`) и правила
   жилья — часть контракта, менять их только вместе с валидатором.
5. Секреты — только в `.env`; в git — `.env.example`.
6. Перед коммитом: `just check` (`cargo fmt --check`, `cargo clippy -- -D warnings`,
   `cargo test --all-targets`) и `bash scripts/qa.sh`.
