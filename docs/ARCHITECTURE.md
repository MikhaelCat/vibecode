# Архитектура

Документ описывает, как устроен проект и где искать код. Он намеренно короткий:
одна страница на каждый слой, без истории разработки и ролей команды.

## 1. Общая картина

```
браузер
  │  POST /api/plan (SSE)
  ▼
src/api ──────────────► src/agent
                          │  tool calls
                          ▼
                     src/tools/providers ──► интернет
                          │  ToolOutput
                          ▼
                     src/domain::Facts
                          │  submit_plan
                          ▼
                     src/domain::plan → validate → repair/fallback
                          │
                          ▼
                     SSE plan ──► src/frontend
```

Ключевое правило: **ни один HTTP-обработчик и ни один кусок фронтенда не
ходит во внешний API напрямую**. Все данные проходят через инструмент,
получают `place_id` и источник, попадают в `Facts` и только потом — в план.
Благодаря этому валидатор может проверить каждую точку.

## 2. Backend

Папки: `src/api/`, `src/agent/`, `src/domain/`, `src/store/`, `src/llm/`.

### API (`src/api`)

- `POST /api/plan` — SSE: `stage`, `intent`, `tool_call`, `tool_result`,
  `plan`, `validation`, `usage`, `refusal`, `done`.
- `POST /api/plan/sync` — то же без стрима, для эвалов и отладки.
- `GET /api/health`, `/api/stats`, `/api/runs/{id}` — диагностика.
- Размер тела ограничен, POST защищён `APP_TOKEN` (если задан), на живой
  LLM стоит семафор и 120-секундный таймаут SSE.

### Агент (`src/agent`)

`orchestrator` — единственный путь к плану:

1. проверить запрос (`guard`, `domain::intent`);
2. собрать компактный контекст (`prompt`);
3. выполнить независимые tool calls параллельно;
4. получить `submit_plan`;
5. развернуть черновик (`domain::plan::enrich`);
6. проверить (`domain::validate`);
7. при ошибках — repair, затем fallback.

Терминальный `submit_plan` не даёт модели «рассказать» план текстом в обход
проверок. Бюджет поисков ограничен, лишние вызовы возвращают ошибку.

### Домен (`src/domain`)

- `intent` — даты (1–7 дней), транспорт, интересы, guardrails.
- `facts` — проверенные места, погода, события, жильё, маршруты.
- `plan` — превращение черновика в дни, дедупликация, переезды.
- `validate` — V01–V15: регион, даты, провенанс, часы, погода, жильё.
- `fallback` — безопасный план из `Facts`, если модель не справилась.

### Хранилище (`src/store`)

SQLite — источник истины:

- `runs` — запрос, статус, задержка, токены, стоимость, `plan_json`,
  `trace_json`;
- `daily_budget` — дневные счётчики.

Redis здесь не используется. Он живёт в `src/tools/cache.rs` и кэширует только
результаты инструментов.

### LLM (`src/llm`)

Один трейт, две реализации: OpenAI-совместимый клиент (Spirit Proxy /
OpenRouter) и детерминированный `MockLlm`. Ключи читаются из `.env`, не
логируются и не сериализуются.

## 3. Parsing

Папка: `src/tools/`.

`registry` задаёт трейт `Tool`, `ToolCtx` и `ToolOutput`; `providers` содержит
по модулю на источник:

| Модуль | Данные |
|---|---|
| `places` | OSM Overpass: природа, музеи, смотровые, еда, отели, бары/клубы |
| `wikipedia` | достопримечательности через geosearch |
| `geo` | Nominatim/Photon: город, село, озеро, река → bbox |
| `weather` | Open-Meteo, fallback VL.ru |
| `route` | OSRM |
| `events` | VL.ru, JSON-LD |
| `lodging` | OSM + `data/mock/lodging.json` |
| `transport`, `fuel` | расписания и АЗС |

Правила парсинга:

- координаты обязательны, конечны и лежат в Приморье;
- `(0,0)` и неизвестные места не становятся точками плана;
- **озеро, река, бухта и море — это районы поиска, а не маркеры в воде**:
  провайдер отбрасывает водные центроиды и возвращает береговые объекты
  (посёлок, пляж, мыс, смотровую);
- бары и клубы попадают в выдачу только по явной категории `bar`/`club`;
- дубликаты убираются по `id` и по названию в радиусе 500 м;
- локальные заглушки читаются только из `data/mock/*.json`;
- каждый результат помечен `live`, `mock` или `stale`.

Кэш (`tools/cache.rs`) необязательный: Redis, при его отсутствии — память.
Ключ включает даты только для погоды и событий.

## 4. Frontend

Папка: `src/frontend/`. Без npm-зависимостей и сборщика: `index.html`,
`styles.css`, `app.js`; `dist/` — копия для axum.

- форма: даты, транспорт, примеры запросов, необязательный токен;
- SSE читается через `fetch` + `ReadableStream`, поэтому работает
  `x-app-token` и корректная отмена;
- план: дни, точки, мини-описания, переезды, жильё, погода;
- карта создаётся лениво через `IntersectionObserver`, тайлы OSM, границы
  Приморья, колесо мыши работает только над картой;
- маркер строится только для валидной точки внутри Приморья; водные
  центроиды и `(0,0)` пропускаются;
- на мобильных однопалый скролл страницы не блокируется.

## 5. QA

- `tests/` — интеграционные тесты валидатора;
- `src/bin/eval.rs` — эвал-раннер и метрики;
- `data/eval/` — запросы и guardrail-кейсы;
- `scripts/qa.sh` — fmt, clippy, тесты, mock-сервер, smoke, браузерный тест;
- `scripts/edge_cases.sh` — живые необычные запросы (отель у маяка, озеро,
  несколько городов, инъекции);
- `scripts/frontend_test.sh` — вёрстка, отсутствие отладочных панелей,
  маркеры и мобильная ширина.

Эвал по умолчанию работает на `MockLlm` и не тратит токены. Живой прогон
включается только явно и требует ключ в окружении.

## 6. Правила изменений

1. Новые данные — только через `Tool` и `Facts`, не напрямую из API/агента.
2. Новые категории — в схеме инструмента, промптах и `ItemKind`.
3. Любая точка плана должна иметь провенанс и координаты в Приморье.
4. Водоёмы не рисуются маркером в воде.
5. Секреты — только в `.env`; в git — `.env.example`.
6. Перед коммитом: `cargo fmt --check`, `cargo clippy -- -D warnings`,
   `cargo test --all-targets`, `bash scripts/qa.sh`.
